# ЗВІТ З ЛАБОРАТОРНОЇ РОБОТИ № 2

**Тема:** Розробка Web API з використанням GitHub Copilot, модульного тестування та TDD  
**Дисципліна:** Моделювання та розробка програмного забезпечення (МРПЗ)  
**Проєкт (з ЛР №1):** «Система керування університетськими аудиторіями» (Company-managed Scrum, префікс `КНРТ`)  

---

## 1. Мета роботи
- Навчитися реалізовувати вимоги до програмного забезпечення, сформульовані у Jira під час ЛР №1, у вигляді програмного коду.
- Отримати практичні навички розробки Web API на платформі .NET 8 із використанням мови C#.
- Навчитися використовувати GitHub Copilot / AI-асистента для аналізу вимог, планування реалізації, генерації та рефакторингу коду, створення тестів і документації.
- Закріпити навички модульного тестування з використанням фреймворку `xUnit` та бібліотеки `FluentAssertions`.
- Практично застосувати методологію **Test-Driven Development (TDD)** і виконати цикл **Red → Green → Refactor**.
- Навчитися організовувати розробку в Git / GitHub відповідно до принципів Git-Flow та зв'язку задач із системою керування задачами Jira.

У лабораторній роботі №1 було створено проєкт у Jira зі схемою **Company-managed (Scrum)** та декомпоновано перший епік «Базовий функціонал керування аудиторіями та бронюванням» на 3 User Story і технічну задачу:

| Ключ Jira | Тип | Назва задачі / Історії | Оцінка (SP) | Опис та Acceptance Criteria |
| :--- | :--- | :--- | :---: | :--- |
| **КНРТ-22** | Configuration Task | Створення структури .NET-рішення | — | Налаштування .NET Solution, Web API проєкту, тестового проєкту xUnit та Swagger |
| **КНРТ-5** | User Story | Реєстрація нової аудиторії | 5 SP | Можливість адміністратора зареєструвати аудиторію із зазначенням місткості та обладнання |
| **КНРТ-4** | User Story | Пошук аудиторій за місткістю та обладнанням | 5 SP | Пошук аудиторій за комбінацією фільтрів (мінімальна кількість місць, наявність проектора тощо) |
| **КНРТ-16** | User Story | Бронювання аудиторії та перевірка перетинів | 8 SP | Резервування приміщення з валідацією інтервалів часу та запобіганням конфліктам розкладу |

### Декомпозиція на підзадачі (Sub-tasks):
1. **КНРТ-5 (Реєстрація):**
   - `КНРТ-6`: Створити модель даних (class) для сутності «Аудиторія» (`Classroom`).
   - `КНРТ-7`: Створити DTO для введення і виведення даних (`CreateClassroomDto`, `ClassroomResponseDto`).
   - `КНРТ-8`: Реалізувати перевірку вхідних даних (валідацію місткості $> 0$, непорожні поля, перевірку дублікатів).
   - `КНРТ-9`: Реалізувати метод Web API для додавання нової аудиторії (`POST /api/classrooms`).
   - `КНРТ-10`: Створити модульні тести для правил реєстрації приміщення (xUnit).

2. **КНРТ-4 (Пошук):**
   - `КНРТ-11`: Реалізувати модель параметрів пошуку для запиту (`ClassroomSearchQuery`).
   - `КНРТ-12`: Реалізувати логіку фільтрації даних у репозиторії (`SearchAsync`).
   - `КНРТ-13`: Створити метод Web API для виконання пошуку (`GET /api/classrooms/search`).
   - `КНРТ-14`: Створити модульні тести для перевірки роботи окремих фільтрів (за місцями та обладнанням).
   - `КНРТ-15`: Створити тести для поєднання декількох умов пошуку.

3. **КНРТ-16 (Бронювання):**
   - `КНРТ-17`: Створити модель даних для сутності «Бронювання» (`Booking`).
   - `КНРТ-18`: Реалізувати алгоритм перевірки перетинів часу в базі даних ($Start_1 < End_2 \land End_1 > Start_2$).
   - `КНРТ-19`: Реалізувати метод Web API для створення запису бронювання (`POST /api/bookings`).
   - `КНРТ-20`: Додати перевірку допустимості часу (час початку не може бути в минулому, $Start < End$).
   - `КНРТ-21`: Створити модульні тести для успішного бронювання та для випадків конфлікту часу.

## 4. Використання GitHub Copilot / AI-асистента

У процесі виконання роботи AI-асистент застосовувався на кожному етапі життєвого циклу розробки:

1. **Аналіз вимог та планування реалізації:**
   - *Промпт до Copilot:*  
     > «Проаналізуй Acceptance Criteria для задачі КНРТ-16 "Бронювання аудиторії та перевірка перетинів". Сформулюй математичну умову перетину двох інтервалів часу та запропонуй структуру валідатора для C# .NET 8.»
   - *Результат:* Сформульовано умову $(Start_{new} < End_{existing}) \land (End_{new} > Start_{existing})$, що покриває всі випадки перекриття інтервалів (повне накладання, початок всередині, кінець всередині, вкладений інтервал).

2. **Генерація модульних тестів за TDD (Red Phase):**
   - *Промпт до Copilot:*  
     > «Згенеруй набір тестів на xUnit з використанням FluentAssertions для валідації реєстрації аудиторії (КНРТ-10). Покрий випадки: від'ємна та нульова місткість, порожній номер, порожній корпус, повторна реєстрація тієї самої аудиторії.»
   - *Результат:* Створено параметризовані тести `[Theory]` з `[InlineData]`, що протестували граничні значення.

3. **Генерація бізнес-логіки та DTO (Green Phase):**
   - *Промпт до Copilot:*  
     > «На основі тестів `BookingTests` реалізуй сервіс-валідатор `BookingValidator` та репозиторій з потокобезпечним збереженням `ConcurrentDictionary`, що повертає `409 Conflict` у разі перетину часу.»
   - *Результат:* Згенеровано чистий код із розділенням відповідальності (SRP).

4. **Документування та Swagger:**
   - *Промпт до Copilot:*  
     > «Налаштуй атрибути `[ProducesResponseType]` та SwaggerGen у `Program.cs` для відображення детального опису контрактів API.»

- **🔴 Red Phase:**  
  Створено тести `BookingTests` на перевірку коректності часу ($StartTime \ge Now$, $StartTime < EndTime$) та на виявлення перетинів часових слотів. Метод `HasConflictAsync` викидав помилку `NotImplementedException`.

  *Результат запуску:*

## 7. Рух задач за Workflows з ЛР № 1

Відповідно до налаштованих у ЛР №1 робочих процесів (Workflow Schemes), задачі пройшли повний життєвий цикл:

- **Для Configuration Task (КНРТ-22):**
  $$\text{To Do} \longrightarrow \text{In Progress} \longrightarrow \text{Verification} \longrightarrow \text{Done}$$
  *(Етап Code Review виключено згідно з правилами ЛР №1).*

- **Для User Stories (КНРТ-5, КНРТ-4, КНРТ-16) та їх Sub-tasks:**
  $$\text{To Do} \longrightarrow \text{In Progress} \longrightarrow \text{Code Review} \longrightarrow \text{Verification} \longrightarrow \text{Done}$$
  - **In Progress:** написання тестів (Red) та реалізація коду (Green).
  - **Code Review:** проведення перевірки у Pull Request / гілці, аналіз коду та рефакторинг.
  - **Verification:** запуск automated tests (`dotnet test`) та перевірка контрактів у Swagger.
  - **Done:** успішне злиття гілки у `main` та виконання Acceptance Criteria.
